# Milestone 3: Cardano network components

This milestone adds the `network-components` crate: three independent Tokio actors for peer
management, header synchronization, and block fetching. The actors communicate through bounded
channels and transport traits, so the same component code runs against either the real Cardano
node-to-node transport or the deterministic fault-injection transport.

The implementation and locally reproducible acceptance suite are complete. A continuous 48-hour
preprod run accepted the version-14 handshake, Keep-Alive, Chain Sync, and Block Fetch flows,
recovered from relay disconnects, stored 47,082 blocks, and passed post-shutdown verification after
172,801.922 seconds. This correctly completes the multi-day preprod Chain Sync run and the preprod
part of the prolonged peer-manager testing requirement.

## Outputs and architecture

The new crate is [`network-components`](../network-components). Its transport boundary is defined
in `transport.rs`; no actor depends directly on TCP or on the simulator.

All actors are spawned independently and return a cloneable handle plus a Tokio `JoinHandle`. State
snapshots use `watch`; chain events use `broadcast`; commands use bounded `mpsc` and `oneshot`
channels. The crate has `#![forbid(unsafe_code)]`.

### Real Cardano transport

`CardanoConnector` uses the workspace `network` crate's type-state mini-protocol handles. A
connection performs:

1. node-to-node version negotiation;
2. immediate Keep-Alive activation;
3. independent Chain Sync and Block Fetch clients;
4. optional Peer Sharing when negotiated; and
5. MUX health propagation to the peer manager.

Completing the transport required making the partially implemented `network` crate a workspace
member and repairing its MUX boundary: complete header reads, correct ingress direction, correct
- arbitrary call numbers to drop;
- every-Nth-call drops; and
- connection loss after a selected number of calls.

`replace_suffix(depth, replacement, payload_bytes)` creates a fork at any retained depth. The next
Chain Sync exchange rolls back to the common point and streams the replacement suffix.

## Automated tests and quality gates

Run the focused suite:

```shell
cargo test --locked -p network -p network-components
cargo fmt -p network -p network-components -- --check
cargo clippy --locked -p network -p network-components \
  --all-targets --no-deps -- -D warnings
```

The final focused run contained four `network` MUX unit tests, three `network` integration tests,
and five component integration tests; all 12 passed. The component tests prove:

- bootstrap discovery and target maintenance under deterministic drops and disconnects;
- synchronization of 2,000 linked headers and recovery from a 1,200-header rollback;
- preference for an arbitrary configured intersection over Origin;
- a 5,000-block selected fetch above the 20,000 blocks/minute threshold and downstream serving;
- rejection of invalid links and rollback to any retained point.

The complete workspace command can also be run:

```shell
cargo test --locked --workspace
```

## Integrated partial-node example

Run all three actors against a deterministic 20,000-block chain:

```shell
cargo +1.97.1 run --locked --release -p network-components \
  --example partial_node -- /tmp/pallas-m3-partial-node.blocks
```

The reproduced run selected and stored 20,000 blocks (5,120,000 payload bytes), maintained three
active peers, discovered three peers, had zero peer/validation failures, and printed
`post-shutdown verification: PASS`. The generated file SHA-256 was:

```text
67427cab69e018d275dd10ff8f48ed1fdb637ae13a1d06128f50ea484a6334ff
```

The file format is a sequence of an eight-byte big-endian length and that block's CBOR bytes. Before
writing, every parsed block is matched to its selected header and header hash. The actors then shut
down, the example rereads the complete file, checks every framing boundary and byte-for-byte block,
rechecks every block/header association, and rejects trailing data.

The peer manager recovered after all 18 observed session losses and ended with a healthy active

no-healthy-peer warnings. The run remained active for more than 48 hours, reported no chain error

The raw log SHA-256 is:

```text
17b2c57c9670c4b974b4b911481eb4958b17ab68713c516e12f20e7bdc7f76db
```

The verified block file, `m3-preprod-48h.blocks`, remained outside the repository because of its size.
Its contents are validated by the recorded post-shutdown verification.

For a fresh run from a recent reviewer-supplied point, append its decimal slot and 64-character
block hash after the duration. Omit both values to start from Origin, as the recorded run did. On
Linux use `/usr/bin/time -v`; for preview, substitute `--preview`, a raw preview relay, and the
output names. A relay hostname can resolve to IPv4 or IPv6. The example advertises initiator-only
diffusion and disables Peer Sharing for the public-relay profile; the peer-manager simulator covers
Peer Sharing independently.

The committed [`preprod-smoke.txt`](M3/preprod-smoke.txt) is deliberately labeled as a 10-second
smoke. It observed one stable peer, 207 stored live blocks, 208 roll-forwards, one initial rollback,
zero peer failures, zero validation failures, and successful post-shutdown verification. Its block
file SHA-256 was:

```text
a263103e97f44183cff044dc1b190019351302f4875f68cf4b8c7edaf428eb5f
```

The 48-hour run intentionally started from Origin to exercise sustained historical streaming.
